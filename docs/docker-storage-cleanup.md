# Docker 数据清理

## 清理前核对

在维护窗口停止 API、worker、协调器和恢复服务，核对 Compose 项目名、实际数据卷和数据库。先运行 `docker system df -v` 与 `docker volume inspect <卷名>`，区分媒体对象、向量数据、队列和 PostgreSQL 数据。

视频可能同时存在于本地对象卷和 MinIO 中。本地录像还可能存在硬链接；目录显示大小不能直接相加，删除单一路径也不一定释放文件占用。

## 保留账号并重置业务

需要明确执行完整业务重置时：

1. 为 core/scenic 两库分别导出表结构，并备份 `users`、`roles`、`alembic_version`；scenic 额外保留 `visitor_accounts`。备份放入私有 `backups/`，不得提交仓库。
2. 在所有写入方停止后，核对表与外键。事务性清空其余业务表，保留账号、密码摘要、角色、游客身份和迁移版本。清除会话后用户需要重新登录。
3. 比较清理前后账号数量与内容摘要，确认保留数据一致。不得只删除录像而保留引用它们的项目、媒体、检测、游览和订单记录。
4. 使用原 Compose 参数执行 `down`，不附加 `-v`。逐一核实并删除该项目的 `backend_objects`、`backend_gallery`、`minio_data`、`milvus_data`、`etcd_data`、`redis_data` 卷；保留 `postgres_data`。仅当 MinIO、etcd、Milvus 为该项目独占时才可以这样重置。
5. 使用原参数重新启动，等待迁移和健康检查完成，确认 `/api/v1/readyz` 的数据库、模型、队列、向量存储和磁盘均就绪。
6. 复核无业务记录、媒体对象和向量遗留，再检查 Docker 占用。新部署会创建少量内部元数据，卷大小不会严格为零。

本节适用于已明确允许删除全部非账号业务数据的维护操作。保留项目或历史业务时，应使用[数据保留策略](DATA_RETENTION.md)，通过业务层同步处理引用与对象。

## 对象存储与磁盘回收

保留 MinIO 服务和部分桶时，必须通过 S3 API 删除对象及所需版本，不能手工删除底层对象文件。完整重置独占对象卷属于另一种操作，应连同相关向量元数据和业务引用一起重置。

构建缓存可按需要清理，但再次构建会重新下载依赖。避免使用全局卷清理命令，以免误删用户数据库或其他项目数据。

Docker 数据卷释放量表示容器存储中的可用空间。Windows Docker Desktop 的虚拟磁盘文件是否立即缩小取决于虚拟磁盘回收机制；不能仅依据 Docker 数字声称宿主盘已经释放同等容量。
